## Changed
- `Dockerfile` and `Dockerfile.maintenance` build with cargo-chef 0.1.78 (installed with `cargo install --locked`). `cargo chef cook` compiles the dependencies in their own layer, keyed on `recipe.json` (the manifests and `Cargo.lock`), and the final `cargo build` compiles only this crate. The GitHub Actions layer cache (`type=gha,mode=max`, already configured) now keeps the compiled dependencies between runs, so a commit that leaves the manifests alone skips them. Before, `COPY . .` came before the only `cargo build`, so every run compiled everything from scratch.
- The `--mount=type=cache` mounts for the cargo registry and `target/` are gone: CI runners never kept them, and a `target/` mount would keep the cooked dependencies out of the cached layer.
- `image.yml` and `maintenance-image.yml` run one job per commit at a time (`concurrency` group on the workflow and `github.sha`, without cancelling). On a push, a run that finds `sha-<commit>` already in GHCR points its missing tags at that image with `docker buildx imagetools create` and skips the build. A release tag therefore re-tags the image that main built for the same commit, and keeps its digest, instead of compiling it a second time. Whichever of the two runs starts first builds, and the other waits in the queue (holding no runner). A `workflow_dispatch` always rebuilds, and so does a push that finds no image.

## Notes
- A re-tagged release keeps the labels of the main build: `org.opencontainers.image.version` is `main` (server image) or the commit sha (maintenance image), not the version. Nothing reads that label; the version is in the tag.
- This replaces the note in `2026-11-19T21-52-56Z-sha-images-on-main.md`: a release tag no longer moves the `sha-` tag to a new image, so no untagged duplicate is left to age out.
- GitHub keeps only one pending run per concurrency group, so two version tags pushed on one commit while its build runs would cancel one of the pending runs. Releases push one tag per commit.
