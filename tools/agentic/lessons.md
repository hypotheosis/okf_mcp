# Lessons from earlier reviews (read before you write code)

Each rule below records a real bug the review bot found in an earlier PR, mostly while building user login (milestone 12). Your code must follow every rule that applies to it, and a test must prove it does. When a review finds a new class of bug, add a rule here in the same PR.

## Locks and races
- **Lock order is always: the user row first** (`FOR NO KEY UPDATE`, or `FOR SHARE` for a guarded insert), then the token, session, passkey or identity rows. Read a child row's `user_id` without a lock, lock the user, then re-check the child under the lock. The rule is documented in `src/store/email_tokens.rs`'s module docs.
- **Every writer of the same rows locks them in one order, on every path, counting the locks `audit::record` takes.** The order is users, then teams, then catalogs and changesets, then the `server_state` row (`bump_admin_generation`), then the rest (a `server_settings` row). Among users it is `users::set_admin`'s and `users::delete`'s: every admin by id, then the others by id. `record` locks users `FOR KEY SHARE` in the middle of your transaction (through `audit_person`, `audit_credential` and `audit_team_ref`): the actor, its credential's owner, the entry's person and a personal team's person. So every store function that records calls `audit::lock_people(&mut tx, actor, &People { target, users, teams, catalogs })` first, naming every user, team and catalog its entry will resolve; it sorts them, then takes each in that order, using the target's requested lock mode and `FOR KEY SHARE` for the rest. Bugs this prevents, all found in review: settings `reset` deleted its row before bumping, which deadlocked against `set`, and both bumped before `record` locked the admin actor, which deadlocked against `set_admin` (PR #416); team and catalog writers recorded a personal team's person or the actor after locking the team or catalog, which deadlocked against the user's deletion, and an actor locked before a lower-id admin deadlocked against `set_admin` (issue #397). When you add a writer, check its order against every other writer of those rows, including a path that ends up writing nothing. Test the pair with the interleaving forced: hold a row one side needs midway (`FOR UPDATE`), queue the change, watch `pg_stat_activity`, take the other side's next lock under a timeout, then release.
- **A self-service deletion re-checks its proof under the user's lock** (`users::delete_own`, issue #355): it takes the asking session's row `FOR SHARE` right after the user row and before any team, catalog or key, then checks the password stamp or passkey still holds. Session rows sit with the user's other children in the order; no writer locks a session row and then a user, team or key.
- **Audit rows are part of the lock order too; refreshing an existing reference must not wait on its audit row.** `audit_person`, `audit_team_ref` and `audit_credential` used to upsert their row on every call; `ON CONFLICT DO UPDATE` locks the existing row even when nothing changes, so admin A inviting B while B invited A (or acting on each other's personal teams through `team_ref`) each held one `audit_people` row and waited for the other's, a deadlock that ordering the `users` rows did not prevent (found in review of PR #419). Since migration `0014_audit_row_locks.sql` a resolver reads an existing row without a lock and refreshes a stale one only under `FOR NO KEY UPDATE SKIP LOCKED`; every user and team gets its row in the transaction that creates it. Never add a SQL function or statement that upserts or updates a shared audit row unconditionally; if a new audit table needs one, give it the same read-first, skip-locked shape. Test it with two actors acting on each other while a third transaction holds one of the rows: both must finish under a timeout.
- **A credential change and its consequences go in one transaction.** Redeeming a link, setting a password or passkey, and revoking sessions all commit together. Hash before you open the transaction, never inside it.
- **Every session insert is guarded against a concurrent credential change.** A password sign-in uses the stamped path (`passwords::Verified { stamp }`, then `user_sessions::start` with `password: Some(stamp)`). Other methods must not create a session that survives a reset or admin change. Ask: if a reset or `set_admin` commits between my check and my insert, does the session still appear? If so, fix it. Test that interleaving deterministically: hold the user row, queue both operations, and watch `pg_stat_activity`.
- **After a commit, await nothing that can block or fail before returning the response:** record success events in the transaction; side effects are in-transaction or detached best-effort.
- **Maps keyed by a client-chosen value** (IP, email, ceremony id) use `ExpiringMap::update_or_insert_sliding` (find-or-create plus change under one lock), never `get` followed by `insert`.
- **Admin level and ceiling come from the user cache on every request** (`App::session_principal`, `Credentials::user`), never from a value read at sign-in.

- **A closure passed to `Ephemeral::update` may run more than once** (a Redis compare-and-set that lost a race reruns it on a fresh copy). It must compute its result from the value alone: clone captured inputs inside it, never `Option::take` or move them out, and do no I/O. Test it by racing two updates of one entry through two Redis handles (milestone 16 plan, Task 2; `shared::ephemeral`'s `a_lost_race_reruns_the_change_on_a_fresh_copy` forces the rerun).

- **Every race test that holds a lock or waits on another task has a timeout** (`tokio::time::timeout`, about 30 s) and fails with a message naming what it waited for. A hung test once stalled a task for 12 hours. Run gates through `tools/agentic/gate.sh`, which enforces a hard timeout. Release held locks on every path, including assertion failures (use a guard or drop the connection).

- **A network test never reserves a port by binding and dropping it.** Between the `drop` and the use, a parallel test can take the port, so the "unreachable" address answers or the server's bind fails. For an address that must refuse connections, use `test_net::Refused::new()` and its `address()`/`port()`: it holds a bound socket that never listens, which refuses every connect and blocks a second bind of the port. Never bind `127.0.0.1:0`, read the port and drop the listener, and never use a fixed "dead" port. For a server that needs a port, let it bind `:0` itself and read the port it chose (`openssl s_server -accept 127.0.0.1:0` in `src/investigator/client_tests.rs` reads it from stdout). Wrap every connect in such a test in `test_net::bounded(what, fut)`, which fails after 30 s naming what it waited for. `test_net` is `pub(crate)`, for tests inside the crate. Issue #769 (PR #1091).

- **Postgres does not wake row-lock waiters in the order they queued.** Two writers queued behind one held row (watched in `pg_stat_activity`) race once it is released: the holder's `UPDATE` leaves a new row version, and each waiter retries against it, so the second can win. A forced interleaving fixes *which locks* each side waits on, never which waiter goes next. Assert what holds in every order: both succeed under a timeout, and the result is a valid serial history (each entry's `from` is the value stored when it ran, and the final state matches the last writer). To force an order, release one side and await it before starting the other. `settings`' set/reset race test assumed FIFO and failed about once in 100 runs alone and more often in full runs (issue #434).

- **An admission decided by catalog name binds to the incarnation it was decided for.** The key cache's gates (memberships, entitlements, unlocks) are loaded by name, and a catalog can be deleted and created again under its name before the cache reloads. A route that is admitted from the gates and then resolves the name again in Postgres (export, import) or writes against a `CatalogState` from a newer map (`open_changeset`) must carry the admitted `catalogs.id` and refuse a mismatch (`Busy`) inside its snapshot or under its lock, before reading or writing anything. A handler-only lookup leaves the race open. In `ToolContext`, every check against a `CatalogState` goes through one helper, `admission_to` (`admit`, `check_contents`, and `one`, which checks the incarnation of what it returns): it decides with gates that know that `catalogs.id` and **returns their refusal; never turn an admission error into `Ok(None)` or an unrecorded success with `.ok()`, `unwrap_or` or `if let Ok`**. A path that queries by `state.id()` without admitting (a changeset list) calls `ctx.check_contents(&state, access)`. Outside `ToolContext` use `catalogs::check_incarnation` (export's and import's `expect_catalog_id`). Test both interleavings: the catalog replaced without polling (stale gates, new rows), and an old principal against a polled new map; check that the replacement is unread, unlisted and unchanged (found in review of PR #442, rounds 1 and 2).

- **A subscriber must never hold the last handle on anything whose `Drop` emits a `tracing` event.** `tracing_core` can drop a subscriber while it holds its dispatcher registry lock (an interest rebuild briefly upgrades every registered subscriber's weak handle), and an event emitted there whose callsite is not yet registered takes that lock again: the whole test binary deadlocks. OpenTelemetry providers emit such an event on drop, even after shutdown. So build every subscriber with OpenTelemetry layers through `telemetry::subscriber::build_with_writer` (or `build`), which keeps its providers until the process exits; never hand a provider to `tracing_opentelemetry::layer()` or `OpenTelemetryTracingBridge` yourself in a test (issue #738).

## Inputs and errors
- **Normalize user text before it reaches SQL.** Postgres rejects NUL, so a NUL becomes a 500. Use `users::normalize_email` and `users::is_lookup_email`. A malformed value must take the same path as "unknown", with the same status, the same body and the same cost.
- **Every refused sign-in looks identical:** the same 401 text, one argon2 check, and no hint whether the account exists.
- **Genuine database errors stay 500.** Don't turn them into 4xx.
- **Bounded state per actor.** When any client, signed in or not, can add entries to a shared in-memory map (flows, ceremonies, pending authorizations), limit each actor: by address for anonymous starts, by user or session for signed-in ones. A new entry from the same browser or session must replace its previous one instead of stranding it. Test that one actor's repeated starts never grow the map and that others can still start.
- **A test that a JSON field is `null` checks the key is there:** `assert_eq!(body.get("notice"), Some(&serde_json::Value::Null))`, never `body["notice"] == Null`. serde_json's `[]` answers `Null` for a missing key, so the weaker form passes when the field is dropped (found while revert-checking issue #364).
- **A new `OkfError` variant is wired in several places, and the compiler names only some of them.** It fails to build until the variant has an arm in `OkfError::kind` and `OkfError::to_json` (`src/error.rs`) and in `AppError::status` (`src/http/mod.rs`): none of the three has a `_` arm, so keep it that way. It builds without these, so check each by hand: (1) the variant's doc comment and `#[error]` message say what the caller should do next; (2) `OkfError::is_internal` lists it if its details must stay in the log (it defaults to not internal); (3) a test in `src/error.rs` pins its `kind()`, its JSON `error` and any extra body fields, like the `ReauthStale` one; (4) an HTTP test asserts the exact status of a route that returns it; (5) `docs/operations.md` names it with its status where each route or tool that returns it is documented, and in the troubleshooting table when an operator can meet it, and `docs/reference/tools.md` names it when an MCP tool can return it; (6) console code that branches on `error.body?.error` (`src/http/ui/js/pages/`) handles it, with a ui_e2e journey. `ReauthStale` (#775, PR #1097) touched every one of these. Issue #1100.

## Browser-facing pages and routes
- **Every state-changing form POST on a server-rendered page** must call the cross-site check in `src/http/signin.rs` (`Sec-Fetch-Site` must be `same-origin` or `none`). This blocks login CSRF. Don't use `Origin`: with `Referrer-Policy: no-referrer`, browsers send `Origin: null`.
- **Cookie-authenticated `/api/v1` writes need `X-OKF-CSRF`.** In the console JS, every request, including raw fetch and XHR uploads, builds its headers through `authHeaders` in `core/api.js`.
- **`return_to` goes through `pages::safe_return_to`.** Test hostile values: `//evil.example`, `https://evil.example`, `/\evil.example`, `javascript:`, and their encoded forms.
- **Request traces log the path only.** Never put a secret in a URL's query if you can avoid it. When it can't be avoided (emailed links), it must still never be logged.
- **No secret reaches a log line or `Debug`:** passwords, tokens, session ids, CSRF tokens, WebAuthn or OIDC state, verifiers, nonces. Give such types a hand-written `Debug`.

## Console behaviour
- **The console uses one credential at a time:** a live cookie session wins over a stored key.
- **Sign-out counts as done only on a 2xx, or a 401** meaning the session was already over. Any other failure keeps the session and shows a retryable error.
- **A browser journey for a write path** must actually perform the write and check the persisted result. It must fail if the header or feature it covers is removed; check that by temporarily reverting the code.
- **Every console control that starts a write is disabled until the write settles, tracked by a stable key, not on the element.** A table re-sort, a list Refresh or a reopened drawer draws a new, enabled button, so a disabled flag on the old one does not stop a second request. Mark controls with `guard(el, key, allowed)` and start writes with `once(key, write)` from `core/pending.js`. Test it by holding the request (`Ui::hold_next`), clicking (`Ui::click_twice`), redrawing (`Ui::mark`, then a sort or Refresh, then `Ui::wait_redrawn`), clicking again, and checking `Ui::held_matches` is 1.
- **A refusal's reason must show even when the read after it fails.** Redraw from the last answer, marked as possibly out of date, and leave every control usable; never let the refresh's success decide whether the reason or the controls come back. Test it with `Ui::fail_next` on the follow-up GET.
- **Overlapping reads draw only the newest answer, and a settled write updates the view that shows its object now.** Number each list or drawer load and drop an answer a newer load has overtaken (a Refresh racing an action's reload). When a write settles, re-render whichever drawer shows the written object now, through that drawer's own ticket, not the drawer the write started in, which may have been closed and reopened. Test with `Ui::hold_answer` (a late answer) and `Ui::hold_next` across a close and reopen. **Take the redraw's number as the write settles, before any other await** (the list refresh): numbered only when the redraw starts, an older write whose list read answered late took the newest number and drew its saved answer over a newer write (found in review of PR #384). Test it by holding the first write's list read (`Ui::hold_answer`) across a newer write. **Scope that number to the drawer or object the write updates:** a page-wide counter bumped by a write of team A cancelled the pending read of team B's drawer, which then never opened. Bump it only while the drawer shows the written object (or number per ticket), and test a write of one object settling while another's drawer is loading.
- **A drawer opened from a table row reads settled state, not the row as first loaded.** A list that is not reloaded after a drawer's write still holds the value it first read, so a drawer opened from it again shows the old value, and the next click sends the write that already happened. Read the drawer's state when it opens (numbered, like any read, and with its controls disabled until that read settles; a failed read leaves them usable, marked out of date), or reload the list after the write. Test it by reopening the drawer **after** the write and its follow-up read have settled, then checking the shown value and that the next click sends the opposite write, once (found in review of PR #445: the catalog drawer's maintenance switch reopened as `on` after turning it off).
- **A failed side read never discards a write's answer, or another read that succeeded.** When a drawer redraws after a write from the write's answer plus another read (the users for a picker), settle each part on its own (`Promise.allSettled`, or a fallback to the previous value), draw the answer, and mark only the failed part as possibly out of date. `Promise.all` rejects as a whole, so a failed users read once threw away a committed suspension and redrew the team as active. Test it with `Ui::fail_next` on the side read after a successful write (found in review of PR #384).
- **A paged list's committed cursor survives a failed or overtaken read.** Keep the rows drawn, the filters they answer and the cursor that continues them as one committed state, replaced only when a first page draws and advanced only when a continuation appends. A pending read only hides Load more; never clear the cursor at the start of a read and restore it on failure: two overlapping Refreshes saved the already cleared cursor, the newer failed, the older was dropped, and the rows lost their Load more (found in review of PR #438). A failed continuation keeps the cursor for a retry and marks the rows possibly out of date like any failed read. Test with `Ui::hold_answer` on one Refresh (or a Load more) and `Ui::fail_next` on the newer Refresh, then check Load more is visible and appends the page once.
- **A journey on a page that loads several sections waits for the whole page before it clicks.** The Account page draws six sections in any order and each moves the controls below it, so a control that is visible is not yet in its final place. Wait for `#main .view[data-loaded=true]` (set once every read has settled), not for the one control you want; after a full-page return from another site (the OIDC link callback) wait for the new page's marker too, once something only the new page shows is there. After a click that sets state the next request reads (a checkbox), wait for the state (`Ui::wait_checked`) before the click that sends it (issue #373).

- **A journey that checks a message the page shows by toggling `hidden`** waits for it to be visible (`ui.wait_visible`), not only for its text: `ui.wait_text` reads `textContent`, which a hidden element still has, so the check passes even when the message never shows (found while revert-checking issue #326).

## Process
- **Find the whole class.** When you fix one path, grep for every sibling path with the same pattern and fix those too.
- **Tests must fail without the fix.** Verify that by temporarily reverting the code, and say so in your report. After restoring a reverted file, `touch` it (or restore with `git checkout`, which sets a new modification time). Otherwise cargo can reuse the test binary built from the reverted copy and report stale results.
- **A bounded call whose output is captured must capture to files, not a pipe.** `x=$(cmd)` waits for end-of-file on its pipe, so a daemonised child or a process that survives KILL, which keeps the pipe open, stretches a "bounded" call past its limit. In `tools/agentic`, use `agentic_gh`/`agentic_git` or `agentic_run_captured` (output to temp files, stdin `/dev/null`, cleaned up on every path), never `$(agentic_run_bounded ...)`; `agentic_run_bounded` is for streaming output only. A test for a bounded call holds the output open from a `setsid` child that ignores TERM and checks the call returns within its limit and keeps the partial output. Issue #1191.
- **A deadline has to include the time to stop what it bounds.** A call capped by the time left before a deadline still needs up to `agentic_kill_after + agentic_reap_after` to be stopped (a call that ignores TERM), so it ended past the deadline. `agentic_call_budget` now takes `agentic_cleanup_reserve` off the time left, and a script whose deadline is its own (`watch-review.sh` diagnostics) adds the reserve to the window it gives itself. A wait that counts a deadline in its message reports the time actually spent. Issue #1169.
- **Never leave a bare stdin reader in a background command.** A background command's stdin is the harness's socket, which never closes. So a `cat`, `read` or `tee` with no input of its own waits forever, writes nothing and uses no CPU. Whatever follows it in the command never starts, often the gate you meant to run, and you wait on a job that will never finish. This happened during #430: a `python3 - <<'EOF' ... EOF` edit followed by a stray `cat > /dev/null;` hung for over two hours. Edit files with the Edit tool or a single heredoc, never a heredoc plus a leftover `cat`. If a background job has written nothing for several minutes, check what it is running (`ps -o pid,etime,comm` on your own PIDs) rather than waiting.
- **An agent saying it waits on background work can have stopped for good.** In M19 the agent for #814 finished its gates, then went quiet: its one hand-back was used, it never answered the follow-up, and its green PR sat unreviewed for about three hours while the coordinator waited. No process was hung, so the watchdog saw nothing. Record every wait with `tools/agentic/expect.sh start <worktree> [label]` (and `done` on the report); the watchdog flags the worktree once it is idle. When it fires, read the worktree's logs and the PR yourself instead of messaging again (issue #850).
- **The PR description and claims must match the final code** exactly. Update them after every review round.
- **Exclusive job fetching is not exactly-once delivery.** apalis's `FOR UPDATE SKIP LOCKED` keeps two workers from taking one job in normal operation, but a call to an outside service whose acceptance was unconfirmed (a timeout) or unrecorded (the success update failed) is retried and can be sent twice. Describe such delivery as at-least-once in docs, comments and the PR, and give the receiver a key to de-duplicate on (the feedback worker sends its row id as `feedback_id`). Found in review of PR #697, which said "two workers never post the same job".

- **A test deadline counts from the moment of the thing it bounds, and a wait is a generous upper bound, not a pace.** A `sleep(300ms)` raced against a condition that needs "some work first" fires early on a machine running several gates (load average 16). Start the deadline once the work it follows is in flight (a token the work cancels), poll a condition with a bound of a minute, and never lengthen a sleep to fit one machine. A test that is about a zero or tiny timeout accepts a timeout of any stage of the start (`pg::is_timeout_class`), and a test that needs one stage to have happened (a container created) repeats the attempt until it did. Issue #500.
- **A fake child's lifetime is controlled by the test, not by a short sleep.** A descendant that "exits after 3 s" makes any assertion about timing depend on how fast the test reaches it; have it wait for a release file instead. Issue #500.

- **A browser journey owns its browser's folder and its lifetime** (issue #1070). `harness::drive` gives Chromium a `--user-data-dir` from a `BrowserHome` and a launcher that applies `PR_SET_PDEATHSIG`, and deletes the folder only after every process using it has exited. Never launch a browser from a test without it: rustwright's own profile folder comes back after it deletes it (one `/tmp` folder per journey), and a browser outlives a test process that is killed. Never print a process's command line when checking for survivors.
- **A journey that signs in as someone else in a second tab must not leave the first account's requests in flight** (issue #1183). The server answers a request with an ended session's cookie 401 and clears the cookie (`unauthorized_clearing`), so a late answer that arrives after the sign-in's `Set-Cookie` signs the new account out again. Post the sign-in from a page with no script (`/healthz`), not the console, and read `/api/v1/session` back before going on (`sign_in_second_in_another_tab`).

- **Register a temp file in the statement that creates it, and defer signals until the helper's one exit** (issue #1193). A trap runs only after a whole statement, so `f=$(mktemp)` then `files+=("$f")` leaves a gap in which a TERM leaks the file; use `agentic_cap_mktemp`. A trap that cleans up mid-flight lets the caller's handler return into torn-down state (four review windows in one PR), so a helper's INT/TERM traps only record the signal; each statement that creates, launches or writes comes directly after its own check (`agentic_cap_live`, with nothing between them) or goes through a helper that checks and then acts (`agentic_cap_mktemp`, `agentic_cap_say`), so a signal lets at most the one statement it lands before run; only the exit (`agentic_cap_finish` / `agentic_signals_end`) removes files, restores the caller's traps and re-raises. See "Signals" in `lib.sh`.

## Events and privacy
- **Every event with error text, caller text or principal text uses `split_event!` (or an explicit `LOCAL_ONLY` twin).** `%error`, `?error`, `reason`, a user name, `actor`, `key_id`, a path, a client id and an IP never go in the exported half; see `docs/contributing/policy-lints.md` "Events". When you audit events, grep the whole of `src/` for `(error|warn|info|debug|trace|event)!(` (a scanner that stops at the first `#[cfg(test)]` module skipped `settle`, and one that skips `src/telemetry/**` skipped three more), and re-run the grep after merging main: other PRs add events (the metrics PR added three with `%error`).

- **A hard-coded poll tick multiplies across fake-clock passes** (issue #1216). `agentic_run_captured` slept 0.1 s between looks, so a watcher on a fake clock (30 passes of 4-5 gh calls) spent 13 s per test on ticks alone, and the suite reached 300 s, its cap. Make a poll tick, a poll interval and a grace period configurable (`AGENTIC_TICKS_PER_SEC`, `AGENTIC_WATCH_POLL`, `AGENTIC_STATE_POLL`), default them to today's values, and measure a limit on the clock, not by counting ticks. Run independent tests in parallel, each with its own world.
