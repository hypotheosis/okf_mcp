# Issue 741: per-action key reads no longer list every key

`me::own` and `keys::managed` read the one credential by id
(`keys::record_by_id`) and then apply the same ownership and `manages`
checks as before; an unknown id and a credential the caller may not act on
still answer alike (404). `me::owned` (`GET /me/keys`, `GET /me/grants`),
`keys::list_keys` (`GET /keys`) and `people::user_detail` (`GET /users/{name}`)
use the new `keys::list_filtered` query, which narrows by user, kind and the
caller's catalog reach in SQL and keeps `keys::list`'s order. The listings
still apply `manages` in memory, so the database only narrows and the
authorization decision is unchanged. There is no paging contract on these
routes, so none was added (responses are unchanged). No migration: the
existing `api_keys_user_id` index serves the user filters; the admin listing
narrows by reach and must read every matching key by design.
